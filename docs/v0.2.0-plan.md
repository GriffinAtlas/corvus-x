# Corvus v0.2.0 — Implementation Plan

**Date:** 2026-03-11
**Goal:** Transform Corvus from a CLI-only tool into a platform: library + CLI + MCP server. Make X API optional. Persist raw data. Add export.

---

## Architecture Change: The Big Picture

Today, Corvus is structured as:

```
CLI commands → hardcoded auth/spinner/process.exit
  └→ buildXxxSnapshot() → core modules (adapters, metrics, differ)
```

After v0.2.0:

```
Library API (corvus-x)           ← new public surface
  ├→ scan(), pulse(), trace(), gather(), read(), scope(), agent()
  ├→ adapters: GrokAdapter, XAdapter
  ├→ compute: metrics, differ, snapshots
  └→ types: all schemas exported

CLI (corvus command)             ← thin wrapper over library
  └→ commands call library API, add spinners/formatting/process.exit

MCP Server (corvus mcp)         ← v0.3.0, thin wrapper over library
  └→ tools call library API, return structured JSON
```

The key insight: `buildXxxSnapshot()` functions are already CLI-independent. They take `{ grok, x }` and return `BuildResult<T>`. The refactor moves them from `cli/commands/` to `core/builders/` and exports them from the package root.

## Phase 0: Fix Pricing Model + Cost Tracking

**Why first:** The hardcoded pricing is wrong and cost tracking is underreporting. Users see inaccurate costs.

### What's Wrong

**1. Tool invocations are separately billed (discovered 2026-03-11):**
- x_search: $5 per 1,000 calls ($0.005/call)
- web_search: $5 per 1,000 calls ($0.005/call)
- Corvus currently tracks ZERO tool call costs

**2. MODEL_PRICING is stale:**
```typescript
// Current (wrong):
'grok-4-1-fast': { input: 0.2, output: 0.5 }
'grok-4': { input: 3.0, output: 15.0 }

// Reality (xAI docs as of 2026-03-11):
'grok-4-1-fast-reasoning': { input: 0.2, output: 0.5 }      // ← name changed
'grok-4-1-fast-non-reasoning': { input: 0.2, output: 0.5 }  // ← name changed
'grok-4.20-beta-0309-reasoning': { input: 2.0, output: 6.0 } // ← was $3/$15
'grok-4.20-multi-agent-beta-0309': { input: 2.0, output: 6.0 }
'grok-code-fast-1': { input: 0.2, output: 1.5 }             // ← new model
```
Note: `grok-4-1-fast` may still work as an alias. Need to verify. Token pricing for it ($0.20/$0.50) hasn't changed, but grok-4 pricing dropped from $3/$15 to $2/$6.

**3. Cached input pricing exists:** $0.05/M for grok-4-1-fast (75% off). Corvus doesn't track this but the API returns actual usage, so our token cost calculation is still correct — it's based on `response.usage` tokens × our price, which might slightly overcount if the API silently uses cache. Acceptable for now.

### What Changes

**`src/core/grok-adapter.ts`:**

```typescript
export const MODEL_PRICING: Record<string, { input: number; output: number }> = {
  'grok-4-1-fast': { input: 0.2, output: 0.5 },
  'grok-4-1-fast-reasoning': { input: 0.2, output: 0.5 },
  'grok-4-1-fast-non-reasoning': { input: 0.2, output: 0.5 },
  'grok-4.20-beta-0309-reasoning': { input: 2.0, output: 6.0 },
  'grok-4.20-beta-0309-non-reasoning': { input: 2.0, output: 6.0 },
  'grok-4.20-multi-agent-beta-0309': { input: 2.0, output: 6.0 },
  'grok-code-fast-1': { input: 0.2, output: 1.5 },
  // Legacy aliases
  'grok-4': { input: 2.0, output: 6.0 },
}

const TOOL_COST_PER_CALL = 0.005 // $5 per 1,000 calls
```

**Cost calculation update** — count tool calls in response:

The OpenAI SDK response includes `choices[0].message.tool_calls` when Grok invoked tools. Count those to estimate tool cost:

```typescript
const toolCalls = response.choices[0]?.message?.tool_calls?.length ?? 0
const toolCost = toolCalls * TOOL_COST_PER_CALL
const costUsd = tokenCost + toolCost
```

**`src/core/types.ts`** — Extend GrokResponse usage:

```typescript
export interface GrokResponse {
  text: string
  usage: {
    inputTokens: number
    outputTokens: number
    costUsd: number       // total (tokens + tools)
    toolCalls: number     // NEW — number of tool invocations
  }
}
```

### Real Cost Impact

| Command | Tool Calls | Token Cost | Tool Cost | Total |
|---------|-----------|------------|-----------|-------|
| ask (x_search) | ~1 | ~$0.0002 | $0.005 | ~$0.005 |
| watch (x_search) | ~1/cycle | ~$0.0002 | $0.005 | ~$0.005/cycle |
| gather (web_search) | ~1 | ~$0.0003 | $0.005 | ~$0.005 |
| scan/pulse/trace (no tools) | 0 | ~$0.0002 | $0 | ~$0.0002 |
| agent (8 steps + plan + synth) | ~2 | ~$0.003 | $0.01 | ~$0.013 |

The agent budget default of $0.10 is still generous. But tool costs are 20x token costs for tool-using commands.

- `src/core/types.ts` — GrokResponse.usage.toolCalls
- `CLAUDE.md` — update pricing documentation

## Phase 1: x_search Parameter Exploitation

**Why first:** Small change, improves every command that uses Grok search. Zero breaking changes.

### What Changes

**`src/core/types.ts`** — Extend `QueryOptions`:

```typescript
export interface QueryOptions {
  model?: string
  enableXSearch?: boolean
  enableWebSearch?: boolean
  systemPrompt?: string
  maxTokens?: number
  xSearchFromDate?: string    // ISO 8601 (YYYY-MM-DD)
  xSearchToDate?: string      // ISO 8601 (YYYY-MM-DD)
  xSearchHandles?: string[]   // max 10 handles, without @
}
```

**`src/core/grok-adapter.ts`** — Populate tool parameters:

```typescript
if (options.enableXSearch) {
  const searchConfig: Record<string, unknown> = {}
  if (options.xSearchFromDate) searchConfig.from_date = options.xSearchFromDate
  if (options.xSearchToDate) searchConfig.to_date = options.xSearchToDate
  if (options.xSearchHandles?.length) searchConfig.allowed_x_handles = options.xSearchHandles

  tools.push({
    type: 'function',
    function: {
      name: 'x_search',
      description: 'Search X posts',
      parameters: {
        type: 'object',
        properties: {
          query: { type: 'string', description: 'Search query' },
          from_date: { type: 'string', description: 'Start date ISO 8601' },
          to_date: { type: 'string', description: 'End date ISO 8601' },
          allowed_x_handles: {
            type: 'array',
            items: { type: 'string' },
            description: 'Filter to specific handles (max 10)',
          },
        },
      },
    },
  })
}
```

**NOTE:** xAI migrated from search_parameters to agent tools. The tool schema declares what parameters Grok CAN use — Grok decides when/how to call them. We're not calling x_search ourselves; we're telling Grok the tool exists with these parameters. This is how the xAI API works: Grok is the orchestrator.

**CLI flags** — Add to `ask` and `watch` commands:

```
--from <date>     Start date (YYYY-MM-DD)
--to <date>       End date (YYYY-MM-DD)
--handle <name>   Filter to handle (repeatable, max 10)
```

### Files Modified
- `src/core/types.ts` — QueryOptions interface
- `src/core/grok-adapter.ts` — tool schema construction
- `src/cli/commands/ask.ts` — CLI flags
- `src/cli/commands/watch.ts` — CLI flags
- `src/cli/repl.ts` — context for filters
- Tests for all of the above

### Edge Cases
- Date validation: reject future dates, reject to < from
- Handle normalization: strip leading @ if present
- Max 10 handles enforced client-side (xAI limit)
- Backward compatible: all new options are optional, existing behavior unchanged

### Unknowns
- xAI's exact x_search parameter behavior is not fully documented. The tool schema tells Grok what's available; Grok decides how to use it. We may need to test against live API to confirm date filtering actually narrows results.
- web_search has `allowed_domains` and `excluded_domains` (max 5 each). We could add `--domain` to `gather` command. Low priority but noted.

## Phase 2: Decouple Core from CLI (Library Mode)

**Why second:** Prerequisite for MCP server, export command, and programmatic use. This is the structural refactor.

### What Changes

**Move build functions from `cli/commands/` to `core/builders.ts`:**

Currently each command file (scan.ts, pulse.ts, etc.) contains two things:
1. `buildXxxSnapshot()` — pure data pipeline, no CLI deps
2. `registerXxxCommand()` — CLI-specific (Commander, spinners, process.exit)

Create `src/core/builders.ts` that consolidates all build functions:

```typescript
// src/core/builders.ts
export { buildScanSnapshot } from './builders/scan.js'
export { buildPulseSnapshot } from './builders/pulse.js'
export { buildTraceSnapshot } from './builders/trace.js'
export { buildGatherSnapshot } from './builders/gather.js'
export { buildReadSnapshot } from './builders/read.js'
export { buildScopeSnapshot } from './builders/scope.js'
```

Each builder file gets the build function extracted from its command file. The command file then imports from the builder:

```
src/core/builders/
  scan.ts      ← buildScanSnapshot() + SYSTEM_PROMPT + metrics computation
  pulse.ts     ← buildPulseSnapshot()
  trace.ts     ← buildTraceSnapshot()
  gather.ts    ← buildGatherSnapshot()
  read.ts      ← buildReadSnapshot()
  scope.ts     ← buildScopeSnapshot()

src/cli/commands/
  scan.ts      ← registerScanCommand() only, imports from core/builders/scan
  pulse.ts     ← same pattern
  ...
```

**Decouple AgentExecutor:**

Replace dynamic imports from `cli/commands/` with imports from `core/builders/`:

```typescript
// Before (agent.ts line 156):
const { buildScanSnapshot } = await import('../cli/commands/scan.js')

// After:
const { buildScanSnapshot } = await import('./builders/scan.js')
```

Replace `ConfigManager.defaultDir()` with constructor parameter:

```typescript
// Before:
const store = new SnapshotStore(ConfigManager.defaultDir())

// After:
constructor(deps, question, plan, options) {
  this.store = new SnapshotStore(options.snapshotDir)
}
```

**Create public API surface (`src/index.ts`):**

## Phase 3: Persist Raw Tweets + Export Command

**Why third:** With library mode done, we can enrich snapshots and add export without touching CLI plumbing.

### Storage Schema Change

**`src/core/schemas.ts`** — Extend `StoredSnapshot`:

```typescript
export interface StoredSnapshot<T extends Snapshot = Snapshot> {
  command: string
  topic: string
  data: T
  raw: string
  timestamp: number
  cost: number
  tweets?: Tweet[]              // NEW — raw tweets from X API
  scores?: GrokTweetScore[]     // NEW — per-tweet Grok analysis
}
```

Both fields are optional for backward compatibility with existing snapshots on disk.

**`src/core/snapshots.ts`** — Extend `save()`:

```typescript
save<T extends Snapshot>(
  command: string,
  topic: string,
  data: T,
  raw: string,
  cost: number,
  tweets?: Tweet[],
  scores?: GrokTweetScore[],
): StoredSnapshot<T>
```

**`src/cli/run-command.ts`** — Pass tweets and scores through:

```typescript
// In runStructuredCommand, after buildSnapshot:
const stored = store.save(
  opts.command, opts.topic, built.data, built.raw, built.cost,
  built.tweets, built.scores,
)
```

### Export Command

**`src/cli/commands/export.ts`** — New command:

```
corvus export <command> <topic>     Export latest snapshot
corvus export --all <command>       Export all snapshots for a command+topic
corvus export --format json|csv|jsonl  Output format (default: json)
corvus export --tweets              Include raw tweets (if stored)
corvus export --scores              Include per-tweet sentiment scores
corvus export --list                List available snapshots
```

**JSON export** — dumps the full StoredSnapshot (or array of them). Direct, lossless.

**CSV export** — flattens to rows. Two modes:
1. **Summary mode** (default): One row per snapshot with aggregated metrics.
   Columns: `timestamp, command, topic, sentiment_avg, tweet_count, engagement, unique_authors, signals, cost`
2. **Tweet mode** (`--tweets`): One row per tweet.
   Columns: `timestamp, tweet_id, author_id, text, likes, retweets, replies, impressions, sentiment, narrative`

**JSONL export** — one JSON object per line (tweet or snapshot). For piping to other tools.

### Files Created
- `src/cli/commands/export.ts`

### Files Modified
- `src/core/schemas.ts` — StoredSnapshot fields
- `src/core/snapshots.ts` — save() signature
- `src/cli/run-command.ts` — pass tweets/scores to save
- `src/core/agent.ts` — pass tweets/scores when saving agent steps
- `bin/corvus.ts` — register export command

### Edge Cases
- Old snapshots on disk won't have `tweets`/`scores` fields. Export handles gracefully: `snapshot.tweets ?? []`
- CSV text field needs quoting (commas, newlines in tweet text). Use proper CSV escaping.
- Large exports (50 snapshots × 100 tweets = 5000 rows). Stream to stdout, don't buffer.
- `--list` reuses `SnapshotStore.listTopics()` (already exists).

## Phase 4: X API Optional

**Why here:** Now that x_search params are working and export captures raw data, we can make structured commands work WITHOUT an X API key by using Grok's x_search as the data source.

### The Problem

Currently, scan/pulse/trace/gather/read/scope all REQUIRE X API. Line 37 of scan.ts:
```typescript
if (!deps.x) throw new Error('X API token required for scan. Run: corvus auth setup')
```

But Grok's x_search can search X posts directly. The difference:
- **X API path**: Fetch tweets ourselves → format → send to Grok for analysis
- **Grok-only path**: Tell Grok to search X AND analyze in one call

### Architecture

Add a second code path to each builder. When X API is available, use the current pipeline (richer data, engagement metrics, user profiles). When it's not, use Grok with x_search enabled and ask it to return the same JSON schema.

```typescript
// src/core/builders/scan.ts
export async function buildScanSnapshot(
  deps: CorvusDeps,
  topic: string,
  maxResults: number,
  pages = 1,
): Promise<BuildResult<ScanSnapshot>> {
  if (deps.x) {
    return buildScanFromXApi(deps, topic, maxResults, pages)
  }
  return buildScanFromGrok(deps.grok, topic)
}
```

**Grok-only path:**
- System prompt includes the same JSON schema
- Adds instruction: "Search X for recent posts about {topic}. Analyze up to 50 posts."
- Enables x_search tool
- Returns BuildResult with `tweets: []` and `scores` from Grok's analysis
- Metrics are estimated from Grok's response (no raw engagement data)

**Trade-off:** Grok-only path has less precise engagement metrics (Grok summarizes rather than providing raw numbers). But it works without a $100/mo API key.

### Files Modified
- All 6 builder files in `src/core/builders/`
- Prompts tuned to ask Grok to include tweet count, engagement estimates
- Tests: add parallel test suites for Grok-only path

### Risk
- Grok's x_search results are opaque — we don't know exactly which tweets it found or how many
- Engagement metrics will be estimates, not exact counts
- Need to clearly document in output when data is from Grok-only vs X API (e.g., `(via Grok)` label)

## Phase 5: XAdapter Timeout + Hardening

**Small but critical.** Currently XAdapter has no fetch timeout — if X hangs, CLI hangs.

### What Changes

```typescript
// src/core/x-adapter.ts
private async fetchWithTimeout(url: string, init: RequestInit): Promise<Response> {
  const controller = new AbortController()
  const timer = setTimeout(() => controller.abort(), 15_000) // 15s timeout
  const response = await fetch(url, { ...init, signal: controller.signal })
  clearTimeout(timer)
  return response
}
```

Replace all `fetch()` calls with `this.fetchWithTimeout()`.

### Files Modified
- `src/core/x-adapter.ts`
- `tests/core/x-adapter.test.ts` — add timeout test
